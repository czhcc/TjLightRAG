# 文档管理设计

## 1. 基线与目标

编写日期 2026-11-04，初始代码基线 `d65cef8`；已同步文档解析模块拆分和三路并行分块索引。依据[设计基线](../DESIGN.md)和文档自动处理代码。对应[文档管理实现](文档管理实现.md)。

以文档列表承载上传、提交文本、查看、重建、删除及暂停/运行。上传后自动完成解析、分块、实体关系抽取、向量生成和完整索引发布，用户无需操作独立任务或索引菜单。

## 2. 页面及权限

| 内容 | 设计 |
| --- | --- |
| 文档表格 | 名称、大小、分块数、状态、操作 |
| 分页 | 默认每页 20 条，可选 10/20/50/100 条，支持前后翻页 |
| 全局按钮 | 上传文档、提交文本，分别打开对话框 |
| 行操作 | 重建、查看、删除；状态区域提供暂停或运行 |
| 动态状态 | 处理中显示转圈与文字，失败显示可理解的原因和重试入口 |
| OWNER、WRITER | 可上传、提交、暂停、运行、重建及删除 |
| READER | 可查看列表及解析文本，写操作禁用，后端仍独立鉴权 |

“查看”显示解析后的纯文本，不是让模型重新生成内容，也不是默认下载原始文件。“重建”重建该行文档的索引，不能悄悄变成全部文档重新运行。

## 3. 输入与上传设计

- 统一通过 Apache Tika 4.2.0 支持 TXT、Markdown、PDF、Word（DOC/DOCX）、Excel（XLS/XLSX）、PowerPoint（PPT/PPTX）、OpenDocument（ODT/ODS/ODP）、RTF、HTML、CSV。单文件非空且最多 5 MiB，TXT/Markdown 需 UTF-8；PDF 提取已有文本层，不启用 OCR。
- 上传对话框支持多选文件、选择目录；目录相对路径保留为来源名称，用于区分不同子目录中的同名文件。
- 文件逐一提交，展示各文件状态；部分失败后重试时跳过已成功文件，避免重复提交。
- 选择文件只加入上传队列，点击“开始上传”才调用服务端。
- 提交文本对话框包含名称、文本、格式、块大小和重叠参数。默认块大小 512 token、重叠 64 token；块大小 16～4096，重叠不得超过块大小一半。

## 4. 处理流程与状态

```mermaid
flowchart LR
    A[上传或提交文本] --> B[保存原始修订与持久化任务]
    B --> C[解析与分块]
    C --> D[自动协调索引构建]
    D --> E[抽取实体关系与生成向量]
    E --> F[验证完整索引代]
    F --> G[原子切换活动索引]
```

列表状态是解析任务、文档控制标志和索引队列的组合投影，不等同于某一张表的单一枚举。

| 典型状态 | 含义 |
| --- | --- |
| pending、processing 等解析任务状态 | 等待或正在解析、分块 |
| processed | 已完成解析与分块，不必然已发布到活动索引 |
| waiting_index | 等待索引协调 |
| indexing | 正在构建或准备发布 |
| indexed | 当前文档修订已进入活动索引 |
| paused | 用户暂停 |
| failed、cancelled | 失败或取消，按界面提示运行重试 |

暂停不删除原文或已发布索引，通过标志和租约隔离阻止过期工作继续发布；运行复用兼容检查点，重建强制重新抽取目标文档。

## 5. 索引一致性及删除

每次发布仍是完整知识库索引代：目标文档使用新处理结果，其他已发布文档复用兼容贡献。模型快照、抽取协议、分块策略、tokenizer 和向量维度必须兼容；不能兼容时明确失败，不扩大为全库重建。

完整新代采用增量计算：实体仍按“名称＋类型”合并，关系仍按规范化后的无向端点对合并。比较合并前的描述、类型、属性、关键词和来源块等原始贡献；贡献未变化的对象直接复用旧摘要和向量，只有贡献变化的对象重新计算。来源块也参与比较，即使描述相同，删除文档导致来源减少时也必须更新来源和关系权重。

重建或删除文档时，以本次完整文档快照重新汇总贡献，移除旧文档独有对象，并保留共享对象中其他文档的贡献。不把旧合并摘要当作新原始贡献，也不在旧权重上累加。名称相同但类型不同的实体分别处理。模型、提示词、tokenizer、补充抽取参数或向量维度不兼容时禁止复用；旧记录缺少贡献摘要时首次重新计算，建立可复用基线。

未变化对象及其向量在数据库内分批复制到新代，变化对象采用批量写入；每批最多 64 个对象，独立短事务检查权限、租约及取消状态，并续期存活租约。构建期间保持 building，部分批次不可用于检索；全部实体、关系及三类向量通过完整性验证后才置 ready，再原子切换活动代。失败重试清理本代部分图谱后重写，不发布部分成功。

通常构建失败保留旧活动代。删除文档是例外：为了让新查询不再读到被删内容，删除时先停用旧活动代，再自动构建剩余文档索引；期间可能暂时无法检索。保留必要的旧来源快照服务重建，不等于业务列表仍显示被删文档。

## 6. 实体关系抽取与依赖

抽取优先覆盖人、地、物、事、网，也接受有依据的其他类型；实体按名称加类型合并，属性包含类型与值，关系端点使用名称及类型解析。实体、关系与来源块保留关联。

单个文本块的首次抽取、补充抽取及纠正合并不设实体或关系条数上限，不因第 41 个实体或第 101 条记录终止。模型应根据原文证据抽取并去重。每轮 JSON 保留 200 万字符大小上限，字段长度、属性、端点和完整性校验继续生效；模型最大输出 token 仍可能限制实际输出。全知识库图谱组装的容量保护（1 万节点、3 万边）与查询分页限制不属于单块抽取条数限制，保持现有规则。

抽取协议升级为 `trs-typed-entity-json-v6`，新索引代使用新协议。已有活动索引继续可用，不混用不同提示词版本的抽取贡献；旧未完成索引需要创建新代重建。

流式 JSON 抽取中的完整对象可写入进度，但只有完整 JSON、语义校验及供应商成功结束全部满足才完成分块。纠正后仍引用缺失实体的关系会丢弃；取消、断流或截断不能发布部分索引。

索引代内部固定最多 3 路并行分块处理。每个任务独立完成该块的首次抽取、可选补充抽取/纠正、块向量和检查点保存，不携带其他块的模型对话历史；有空位才派发下一块，不把整个索引代排入线程池。已完成且兼容的块直接复用。

所有分块成功后，按数据库原有 `chunk_id` 排序汇总抽取贡献，统一执行实体关系合并、摘要、图谱向量和完整索引发布。这里的固定合并顺序不是文档内的 `chunk_order`，也不是线程完成顺序；并行只改变分块执行调度，不修改实体身份、关系合并、来源关联或检索算法。

任一块失败即停止补位并取消其他在途任务，等待它们退出后结束该轮构建；等待期间持续检查租约和权限。暂停、取消、撤权及租约失效均禁止后续检查点或索引发布，数据库写入保留原有 fencing 校验；已经保存的完整检查点供后续兼容重试复用。并发数 3 是单实例单索引代的上限，多实例部署仍通过数据库租约协调，模型服务需承受实例合计并发。

需要配置抽取、摘要及向量用途，详见[模型配置设计](模型配置设计.md)。补充抽取、图谱合并及摘要会影响处理时长，文件字节小不代表只调用一次模型。

## 7. 文档解析模块边界

服务端通过独立 Maven 模块 `document-parser` 提供文档解析能力，与 `common` 并列，均由 `app` 按需依赖，`bootstart` 通过 `app` 引入。模块仍与业务在同一 JVM 中运行，不增加远程调用。

- 解析模块通过 Tika 检测允许格式并提取正文，校验实际格式与扩展名一致。TXT/Markdown 保留严格 UTF-8、BOM 去除、原始换行和标题层级。输出统一为纯文本，来源位置指向持久化解析文本的 Unicode 码点。
- 解析结果及来源结构 `ParsedDocument`、`HeadingRef`、`ChunkPiece`，以及安全错误码 `ProcessingFailure` 由解析模块提供。`ChunkPiece` 是分块算法与标题关联共用的数据载体，分块算法仍属于 app。
- 模块不依赖 Spring、数据库、HTTP 或模型服务；app 通过配置类注册解析器，负责上传校验、持久化任务、租约、token 分块和索引业务。
- 新修订采用 `tika-4.2.0-source-v1`，旧 `txt-flexmark-v1` 修订和检查点仍可恢复，不改写已有块或来源记录。原始文件单独保存，查看、分块和检索使用解析文本。
- 不递归提取附件，不调用 OCR 或视觉模型。加密、损坏、格式不符和无正文文件明确失败；输出最多 5,242,880 个 UTF-16 字符，解析回调检查取消。解析仍在同一 JVM 的任务线程中执行，没有独立进程隔离或硬超时。

## 8. 验收要点

多文件/目录上传、上传后自动构建、解析文本查看、列表翻页、行级运行范围、暂停后立即继续的租约隔离、失败保留旧代、删除后的索引停用、只读权限和切换知识库清理对话框均应验证。

模块迁移还需验证可独立执行解析单测、应用能注入唯一解析器、原有分块与标题关联测试通过，以及发布包包含解析模块。
